# AGENTS.md for `@agntn/puzzles`

## Scope

Repository-wide operating contract for agents changing this package. It supplements higher-priority safety and user instructions. A nested `AGENTS.md`, if introduced, overrides this file within its directory.

`@agntn/puzzles` is a dataset kept as code of public crypto bounties, puzzles, and challenges. Every puzzle is a typed record built by `puzzle()`; a collection is a list of those puzzles. The library, CLI, MCP server, and the Pi/OMP extensions all read the same registry. There is no build-time data artifact and no editable JSON.

## Architecture

- `src/core/puzzle.ts` holds the abstract `Puzzle`, the chain bases (`BitcoinPuzzle`, `BitcoinCashPuzzle`, `ECashPuzzle`, `EthereumPuzzle`, `BasePuzzle`, `LitecoinPuzzle`, `DogecoinPuzzle`, `DecredPuzzle`, `ArweavePuzzle`, `MoneroPuzzle`), `Status`, `toJSON()`, and the `PuzzleSpec` record with the one `puzzle()` factory, which reads a string address on the record's required `chain`.
- `src/core/parts.ts` holds the constructors a puzzle class calls: addresses (`addressOn()`, which reads a string on its chain, and the builders `p2pkh`, `p2sh`, `p2wpkh`, `p2wsh`, `standard`), pubkeys, transactions, assets with the `digest()` that pins each file's bytes, stages with their `artifact()` entries (a stage artifact is a file the author published, not a generated data artifact), parties, hints (`official`, `community`, `confirmation`), techniques (`technique`), and the chained `Key` builder. `src/core/technique.ts` holds the `Technique` vocabulary a technique names.
- `src/core/collection.ts` freezes and indexes the puzzle list and implements lookup, filters, balances, and verification once.
- `src/core/registry.ts` is a lazy manifest registry: a table seeded on first use from `builtins` in `src/collections/index.ts`, where each entry is a key plus a literal `import()` of the collection module. Keys, aliases, and `hasCollection()` answer synchronously; instances load on the first lookup for their key.
- `src/core/dataset.ts` computes the asynchronous aggregate views `all()`, `selectPuzzles()`, `get()`, `collectionSummaries()`, `stats()`, `dataVersion()`, `dataset()`; the cached ones are memoized per loaded snapshot, so a registration invalidates them by identity.
- `src/core/chains.ts` narrows `@agntn/chains` to the ten supported chains and reads names, symbols, decimals, explorer bases, and the address and txid format checks from it.
- `src/core/balance.ts` holds the balance contract (`BalanceOptions` and the error classes); `src/core/providers.ts` maps each chain to its `@agntn/explorers` provider (Monero has none yet), Ethereum to Etherscan with a key and to Blockscout without one, Base to Blockscout alone, gives Bitcoin one Blockstream fallback and Litecoin one Blockchair fallback after a transport failure, a rate limit or a 5xx, asks the fallback first for ten minutes once it answered in the primary's place (`forgetFailedHosts()` clears that between unit tests), keeps a fallback that reads no keys out of public key lookups, reads balances, transaction histories and the key a spend showed through that one choice, and is imported by `Puzzle.balance()` and `watcher()` on first use.
- `src/core/watch.ts` compares a puzzle with its chain (transactions the record misses, an unsolved prize the addresses no longer hold, a key an unsolved target showed that the record lacks or spells otherwise, asked only once the target spent) and, given `since`, with its source page through `src/core/sources.ts`, which reads Wayback captures with `@agntn/archives`. `formatWatchReport()` writes the rows `puzzles watch` and `puzzles_watch` share. It reports and never edits a record. `src/core/eligibility.ts` builds the checklist record behind `puzzles eligibility` and `puzzles_eligibility` from a puzzle or a bare address: the record's fields, a live read of every prize address through `lookupAddress()`, with the explorer's lifetime totals, and a `missing` line per field nobody can fill.
- `src/core/archived-sources.ts` indexes the reading copies under `assets/sources/` and finds the ones a puzzle cites, by exact URL or tweet ID, in its record, its collection's hints and techniques, and its collection's author. `src/core/files.ts` lists a puzzle's files with those copies and reads one: the copy its link names first, then `main`'s for a file merged since, then for a pinned file the author's URL and the archive capture, returning only the pinned bytes. `puzzles assets` and `puzzles_assets` share both.
- `src/core/asset-ref.ts` picks the ref every asset link names: the release tag in the npm package, the commit in a checkout and on the docs site, where the tag lacks every file merged since. The commit is one global, because a built bin in a checkout runs `dist/` and `src/` side by side. `src/checkout.ts` sets it from `git merge-base HEAD origin/main` for `src/cli.ts` and the Pi and OMP extensions, and `docs/server/plugins/asset-commit.ts` from the build's commit.
- `src/core/verify.ts` resolves a record's secret and compares the derived address; `src/core/crypto.ts` maps each chain to its `@agntn/keys` wallet and translates a record's pubkey format and address kind into keys' options. Curves, checksums, WIF and seed derivation live in keys.
- `src/collections/index.ts` is the manifest; `src/collections/<key>.ts` is a collection: author and the puzzle list, published as `@agntn/puzzles/collections/<key>` and bundled as its own input.
- `src/collections/<key>/<name>.ts` is one puzzle record built with `puzzle()`. Singleton collections keep their single puzzle in the collection file.
- `src/cli.ts` is the `puzzles` entry point: `runCli` from `@agntn/tools/cli` over `puzzlesTools`, with the package commands of `src/commands/index.ts` in place of the tool commands of the same name. Each of those is a `defineTool` only the CLI gets, because the command line keeps URLs, every match, filtered passes, rows as they land and its exit codes; `stats` and `collections` are the tools themselves, and `author` and `solver` run their executors. Inside a checkout, the built `dist/cli.mjs` serves `mcp` from `src/mcp.ts`, like the Pi and OMP extensions, so a local server needs only a restart after a change. The npm package ships no `src/` and runs the bundle, and so does a copy under `node_modules`, where Node does not strip types. `PUZZLES_DIST=1` forces the bundle. A change to `src/cli.ts` itself still needs `pnpm build`; `test/eval-packed.ts` runs `mcp` in each of these layouts.
- `src/tool-operations.ts` implements every agent tool once, holds the `facts` table the definitions read (names, prose, parameter constraints, the status list), and enforces those constraints in the executors.
- `src/tools.ts` declares each tool once with `defineTool` from `@agntn/tools`, its schema built with `Type` from the same package, plus `callSummaries` for the OMP call line.
- `src/mcp.ts` serves that list through `createMcpServer` from `@agntn/tools/mcp`. The remote server at `puzzles.agntn.dev/mcp` (`docs/server/mcp/`) hands `publicPuzzlesTools` from `src/tools.ts` to `toToolkitTools` from `@agntn/tools/toolkit`, so a new tool needs no edit there. That's the same list with `puzzles_verify` held to one `id`, because a filtered verify costs seconds of the worker's CPU per request. `toolListings` and `callTool()` in `src/mcp.ts` list and run that subset too, and `test/unit/docs-mcp.test.ts` holds the site to them. Both servers introduce themselves with `serverInfo` from `src/server-info.ts`, a pitch and the site's icons on top of name and version, so a connector card isn't just a name.
- `packages/{pi,omp}/extensions/puzzles.ts` hand the same list to `registerPiTools` and `registerOmpTools`.
- `build.config.ts` configures obuild, which emits every entry as one bundle so they share the registry and core chunks under `dist/_chunks/`. `vite.config.ts` configures Vite+ for `vp lint`, `vp fmt` and `vp test`.

## Invariants

- **Source of truth:** puzzle data lives in the collection modules' `PuzzleSpec` literals and nowhere else. Never reintroduce a generated JSONC artifact or a second data module that mirrors them.
- **A puzzle answers, it does not describe:** consumers read through methods: `id()`, `address()`, `sourceUrl()`, `startedAt()`, `chain()`, and the computed ones. The data itself is one `PuzzleSpec` literal handed to `puzzle()` with its required `chain`; a hand-written subclass of a chain base stays valid for a puzzle that needs behavior of its own.
- **No nulls:** absent data means no spec field and no key in the serialized record. `toJSON()` omits, never nulls.
- **Status is explicit:** it defaults to `unsolved` and cannot be derived, because a claim transaction plus a published key still means `solved`.
- **Parts, not literals:** build keys, transactions, assets, parties, and hints with the `parts.ts` constructors so optional fields stay absent instead of empty. An address is a string that `addressOn()` reads on the record's chain into its kind and HASH160; a builder stays only for what a string cannot carry, a published redeem script or a CashAddr. A hint records who gave it and where; its `source` is the publication evidence. Optional `confirmation` links to an archive or another publication of the same hint by its author, not a solver's reconstruction or general puzzle context. Do not require a second URL or invent corroboration. A hint never records whether it is right. A published answer belongs in its optional `answer` part, with its own source and optional publication date, never in the original hint text or automatically in the puzzle's key. A hint that holds for every puzzle of a collection lives on the collection once, as the fourth constructor argument, and `Collection.hintsById()` joins it with a puzzle's own. A technique is a name from the `Technique` vocabulary plus the page that says it was used, the author's recipe or a published solution, never a guess: on a stage, on a record, or once on the collection as the fifth constructor argument, joined by `Collection.techniquesById()`. `test/unit/validation.test.ts` checks the vocabulary and the sources, and runs the recipes a record holds against its tags.
- **Solvers join by key:** a named solver carries a kebab-case `key` on every puzzle it solved, with the same name and kind; `solvers()` in `src/core/dataset.ts` joins those records into one entry, scalars from the first record and list items once each, so a fact lives on the puzzle it is about. A solver known only by an address has no key and no entry. A solver key equal to an author key is the same party, and `test/unit/validation.test.ts` checks both.
- **Records stay as written:** the factory freezes the spec through with `frozen()` from `parts.ts`, `Key` freezes its data, `Collection` freezes the author, and `toJSON()` and the memoized dataset views freeze what they build, so every accessor hands back immutable data and the views memoized per registry snapshot stay true. New parts are plain objects and arrays, which the freeze walks; a class with private state freezes its own.
- **Registration is a lazy manifest:** `src/collections/index.ts` lists `{ key, load }` entries and imports no collection module statically; `src/core/registry.ts` seeds its table from that list on first use, so importing the package has no side effects and `sideEffects` names only the CLI entry. `registerCollection()` stays open for instances and for `{ key, load }` entries. A new collection needs a `static readonly key`, a manifest entry, and nothing else: `build.config.ts` reads the directory and `test/unit/library.test.ts` compares the modules on disk with the manifest and loads each entry.
- **Views are asynchronous:** everything that needs instances (`collections()`, `getCollection()`, `all()`, `get()`, `stats()`, `dataVersion()`, `dataset()`, the tools, the commands) awaits the loads; `collectionKeys()` and `hasCollection()` stay synchronous on the manifest. The root entry never re-exports a collection; consumers import one from `@agntn/puzzles/collections/<key>`.
- **One registry:** `src/core/registry.ts` is the only registry. Keep the `peter_todd`, `warpwallet` and `b1000` aliases and the snake_case keys of the collections renamed to kebab-case.
- **Identifiers:** IDs stay `collection/name`, both segments kebab-case, like file names, asset directories and docs URLs; a singleton ID is its bare collection key, such as `gsmg`, `movie-enigma` or `genesis`. A collection resolves a query only in the spelling its identifier uses, `71`, `"71"` or `"bits/71"`, never a `Number()` reading such as `"0x47"` or `"7e1"`, and a query of another type is a miss, not a `TypeError`.
- **Data version:** `dataVersion()` is the first 12 hex characters of SHA-256 over the serialized collection array. It must stay free of timestamps and environment data.
- **Runtime split:** `src/core/` and `src/index.ts` stay neutral ESM with no APIs that need Node. Code that needs Node belongs to `src/cli.ts`, `src/checkout.ts`, `src/commands/`, and `src/mcp.ts`. The one exception is `src/core/sources.ts`: `@agntn/archives` reads its config through `c12` and `node:fs` on every archive read, so it runs on Node or on a worker that keeps `node:fs` native, as `docs/nuxt.config.ts` does. `watch.ts` imports it only when `since` is given, so the package import and a watch without `since` stay neutral.
- **Balances:** `Puzzle.balance()` is the one entry; collections forward to it. Base units are `bigint`, providers come from `@agntn/explorers` and load on the first lookup, and API keys are redacted from every error. Tests stub `globalThis.fetch` instead of injecting a transport.
- **Verification:** expected verification failures are values, not exceptions.
- **CLI output:** a command answers with its lines as text and its data as `details`, which `--json` prints; a command that streams rows or bytes writes them through `src/commands/output.ts` once `streams(host)` says the caller asked for text. A failure a script should see sets `process.exitCode` on a normal answer, and a refusal throws a `PuzzlesError`, which `runCli` prints as one line. `runCli` refuses an option a command does not declare, and `plainWord()` refuses a dashed word it would hand to a positional, since no identifier starts with a dash. A command imports the core inside `execute`, because `runCli` builds every definition before it reads the line. `mcp` stays open to any flag but `--help`.
- **Tools:** add an agent tool once: the executor and its `facts` entry in `src/tool-operations.ts`, the definition in `src/tools.ts`; MCP and both extensions never restate a name, description, limit, or status list. `@agntn/tools` checks every call against the schema on all three surfaces, and the executors still enforce the same limits and throw `InvalidArgumentError` for a caller of `@agntn/puzzles/tools`; `test/unit/tool-schemas.test.ts` pins both sides. Build schemas with `Type` from `@agntn/tools`, never a bare `typebox` import, which OMP rewrites to its omptype facade. A schema with parameters is closed, so a misspelled filter fails instead of widening the answer; the tools without parameters stay open. Discovery is one contract: `puzzles_collections` prints the rows of `puzzles collections`. `puzzles_show`, `puzzles_stages`, `puzzles_hints` and `puzzles_eligibility` share their formatters with the CLI but name a shipped file by its repository path and, when the puzzle has a file or an archived source to read, end with a `files` line that points at `puzzles_assets`, so a model reads the pinned bytes instead of downloading a URL; the CLI keeps the URL.
- **Extensions:** their factories are asynchronous because they load `tools` first through literal `import()` specifiers, `src/` in a checkout and `dist/` when installed; their types come from `src/`, so typechecking them does not depend on a fresh `dist`. The OMP one takes `Text` from the host package root and registers every tool with `loadMode: "essential"`, so OMP keeps them in its top-level list instead of behind discovery. Error text goes through the sanitizer of `@agntn/tools` on MCP and quotes echoed values.
- **Verification is lazy:** `verify()` is asynchronous and imports `crypto.ts` on its first call, so keys stays out of the package import and of CLI startup; keep every other module free of static imports from `crypto.ts`. `runCli` builds every command for `--help` and for an unknown command, and `test/eval-packed.ts` checks that `puzzles --help`, the library import and a lookup load no keys, while the first verification does.
- **Tests share module state:** the `test` block of `vite.config.ts` sets `isolate: false`, so a test that mutates the registry works on a fresh module graph (`vi.resetModules()` plus a dynamic import) and resets the graph again when it is done.

## Change routing

- New puzzle: add `src/collections/<key>/<name>.ts` exporting a record built with `puzzle()` and its `chain`, then import it and append it to the collection's `puzzles` list. New export names use concise camelCase, preserving the publisher's word boundaries, for example `luckyLurkerVault2`, without a redundant `Puzzle` segment; the file name is the identifier segment.
- Puzzle data fix: edit the one record. `test/unit/validation.test.ts` re-checks identifiers, address and txid formats, key material, BIP38 payloads, claimed and swept public keys, asset paths and their pinned SHA-256 and size, and the no nulls rule.
- New solver: give the `party()` on the puzzle a kebab-case `key`, its `kind` when known and at least one sourced `fact`; a second solve repeats the key and adds only its own facts. Add `docs/content/4.solvers/<n>.<key>.md` with `::solver-facts{solver="<key>"}`.
- New collection: follow the registration invariant, add its author with `party()` and any collection-wide hints as the fourth constructor argument, add its `{ key, load }` entry to the manifest, and extend `test/unit/library.test.ts`.
- New puzzle field: add the method to `Puzzle` with a safe default, extend `toJSON()`, `PuzzleSpec`, and the internal spec-backed puzzle, then teach `parts.ts` how to build it.
- New CLI command: a new tool already gets one. A command only the CLI needs goes into `src/commands/<name>.ts` as a `defineTool` with its `cli` hint, into the list in `src/commands/index.ts`, and into `test/unit/cli.test.ts`.
- New agent tool: implement it in `src/tool-operations.ts` with its `facts` entry, add its `defineTool` to `puzzlesTools` in `src/tools.ts`, extend the tool test files.
- New technique: add the name to `Technique` in `src/core/technique.ts` with its one line, tag the records whose sources state it, and update the counts `test/unit/library.test.ts` pins. The CLI flag and the tool enum read the list.
- New public export: add it to `src/index.ts`; build before checking extensions because they resolve `dist/index.d.mts`.
- Commit and PR scope is the layer, never the element. Anything under `src/collections/` is `collections`, with the collection or puzzle identifier in the subject: `feat(collections): add movie-enigma`, `fix(collections): bits/135 solved`. Code takes the module name (`verify`, `dataset`, `cli`, `tools`), so the scope vocabulary stays a dozen names and never grows with the dataset.

## Proof before handoff

```bash
pnpm lint
pnpm typecheck   # builds first, then checks src, Pi, and OMP
pnpm test
pnpm test:packed # packs the tarball and runs every published entry without src/
node src/cli.ts collections
```

`node src/cli.ts collections` must list every collection in the manifest. Node.js 26 or newer runs the TypeScript sources directly; no loader is required.

## Known debt

Do not mistake these for intentional architecture:

- `dataVersion()` serializes the whole dataset on first use.
- Puzzle accessors rebuild their parts on every call; only the instances themselves are cached.
- Pi and OMP wrappers keep their own loader because OMP cannot re-export another module's extension; the definitions they register come from `src/tools.ts`.
- Balance lookups have no retry of their own and no fallback beyond Bitcoin's one to Blockstream and Litecoin's one to Blockchair, whose ten minute memory lives in the module, so it spans every pass and MCP request of one process; the timeout and the rate limit backoff are what `@agntn/explorers` providers bring.
