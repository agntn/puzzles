## The call

```ts
import { b1000 } from "@agntn/puzzles/collections/b1000";

const balance = await b1000.require(71).balance();

balance.chain; // "bitcoin"
balance.confirmed; // 710022600n, base units
balance.unconfirmed; // 0n, a signed mempool delta when the provider reports one
balance.total(); // 710022600n
balance.totalUnits(); // 7.100226, a double, so 18 decimal places would round
balance.totalAmount(); // "7.100226", every digit, whatever the chain
balance.decimals; // 8, from @agntn/chains
```

Every puzzle answers `balance()`. Collections forward `balance(query)` and `balanceById(id)` to it. The providers come from [`@agntn/explorers`](https://explorers.agntn.dev) and load on the first call, so importing the package carries no network code.

Some prizes don't sit where the key leads. The key opens a wallet, and the wallet has to pull the prize out of a contract. Such a record names the contract as `escrow`, and `balance()` adds both addresses up. That's what the key is worth. If either lookup fails, the whole call fails. Half a prize is a wrong number, not a smaller one.

| Chain        | Provider                                   | Needs                                                                     |
| ------------ | ------------------------------------------ | ------------------------------------------------------------------------- |
| Bitcoin      | Mempool at mempool.space, then Blockstream | nothing                                                                   |
| Litecoin     | Mempool at litecoinspace.org               | nothing                                                                   |
| Bitcoin Cash | Blockchair                                 | nothing, until Blockchair blacklists your IP. Then a key                  |
| eCash        | Blockchair                                 | the same as Bitcoin Cash, and the same key                                |
| Ethereum     | Blockscout, or Etherscan V2 with a key     | nothing. An Etherscan key moves it to Etherscan                           |
| Base         | Blockscout at base.blockscout.com          | nothing, and a key changes nothing                                        |
| Decred       | Dcrdata                                    | nothing, and patience: dcrdata answers a fresh address in 6 to 11 seconds |
| Arweave      | the arweave.net gateway                    | nothing                                                                   |
| Dogecoin     | Blockchair                                 | the same as Bitcoin Cash, and the same key                                |
| Monero       | none                                       | rejects with `UnsupportedChainError` before any request                   |

Bitcoin has a spare. mempool.space drops lookups now and then, and a long pass is where it happens most. A timeout, a refused connection, a rate limit or a 5xx sends the same lookup once to Blockstream at blockstream.info. A rejected address or a balance that doesn't parse goes nowhere else. Another host would say the same. If Blockstream fails too, the error names both. Each host gets the whole `timeout`, so two timeouts in a row take twice as long.

Ethereum picks its provider by the key. Without one, Blockscout at eth.blockscout.com answers and nobody needs an account. Pass an Etherscan key and the lookup goes to Etherscan instead, and Blockscout never sees that key. Both read the same chain, so they agree to the wei. Neither is the other's spare, though. A failed Blockscout lookup fails, it doesn't go knocking at Etherscan.

Base doesn't pick. Etherscan V2 moved Base behind its paid plans, so a free key would turn a working lookup into a refusal. Base always asks Blockscout, and any key you pass stays home.

## Options

```ts
await puzzle.balance({
  apiKey: "your-etherscan-key",
  baseUrl: "https://mempool.example", // another instance of the same provider, and no fallback
  timeout: 30_000, // milliseconds, the providers default to 15 seconds
});
```

That's the whole options object. There's no `fetch` to inject. The providers read `globalThis.fetch` when they run, so a test stubs the global and a runtime brings its own. Leave `apiKey` out and Ethereum goes to Blockscout. A `baseUrl` goes to whichever provider the key picked, so a keyless one has to be a Blockscout instance.

## Errors

```ts
import {
  BalanceError,
  BalanceProviderError,
  InvalidAddressError,
  UnsupportedChainError,
} from "@agntn/puzzles";
```

All three descend from `BalanceError`, which descends from `PuzzlesError`. `InvalidAddressError` is a provider or `@agntn/chains` saying the address doesn't fit. `UnsupportedChainError` is Monero, for now. `BalanceProviderError` is everything else: a transport failure (on Bitcoin, from both hosts), a not numeric balance, a rejected key. An API key never appears in an error message. It's replaced with `REDACTED`, and the original error isn't attached as `cause`, so it can't leak through a logger either.

## CLI and tools

```bash
puzzles balance b1000/71                       # b1000/71: 7.100226 BTC
puzzles balance arweave/weave11                # Ethereum through Blockscout, no key
puzzles balance arweave/weave11 --api-key …    # through Etherscan, or set ETHERSCAN_API_KEY
puzzles balance b1000/71 --json                # { chain, confirmed, unconfirmed, decimals }
puzzles balance --status unsolved              # one row per open prize
puzzles balance --collection b1000 --json      # [{ id, chain, confirmed, … }, { id, chain, error }]
```

Without an id, `balance` takes the filters `list` takes: `--collection`, `--address`, `--chain`, `--status` and `--with-pubkey`. It asks one explorer after another, a quarter of a second apart, because a burst of 90 requests is how mempool.space starts dropping them. Each puzzle gets its own row, `OK	b1000/71	7.100226 BTC` or `FAIL	b1000/72	Balance lookup failed: …`, printed as soon as the answer comes back. A failed lookup doesn't end the pass. The command exits 1 at the end, so a script knows to run the `FAIL` rows again. With neither an id nor a filter it refuses instead of asking about every puzzle in the dataset.

Each chain reads its own key: `ETHERSCAN_API_KEY` for Ethereum, `BLOCKCHAIR_API_KEY` for Bitcoin Cash, Dogecoin and eCash. `--api-key` beats both and goes to every chain in the pass, so for a mixed set leave it out and set the two variables. Your Etherscan key never lands at Blockchair that way.

`puzzles_balance` is the same call for a model, and it answers with the same line, `b1000/71: 7.100226 BTC`. The symbol is the chain's own coin. `arweave/weave9` pays 100 DAI, and its balance is the ETH at that address, not the DAI. `puzzles_balance` is annotated as open world, because it reaches beyond the bundled dataset. So is `puzzles_watch`, below.

## What changed since the record?

A balance is the present. A record is the past someone wrote down. They drift apart quietly. Somebody tops up a prize. Somebody spends from it. The author edits the page. Who notices? Usually nobody, for months.

`watch` notices. It reads the chain and lays it over the record:

```bash
puzzles watch bitaps                          # OK	bitaps
puzzles watch b1000/71                        # DEPOSIT and BALANCE rows, see below
puzzles watch --status unsolved               # every open prize, a quarter second apart
puzzles watch --collection genesis --json     # [{ id, chain, findings, errors, truncated }]
puzzles watch b1000/71 --since 2026-09-01     # the source page too
```

Each finding is one row. On 2 October 2026, `b1000/71` printed these, among others:

```
DEPOSIT	b1000/71	572001d88e5c3030a89fe119e62cf80892876b59dcb9efe91348dd38745147e1 0.00000666 BTC 2026-09-29T22:18:51.000Z at 1PWo3JeB9jrGwfHDNpdGK54CRas7fsVzXU
BALANCE	b1000/71	7.1019168 BTC held, 7.100226 BTC recorded as the prize
```

A `DEPOSIT` or a `SPEND` is a transaction the record doesn't list. `TRANSACTION` is one where the explorer won't say which way it went. `BALANCE` is an unsolved prize the addresses don't hold anymore, compared at the precision the record keeps. Only an unsolved puzzle gets that check. Any other prize is history, not a promise.

`watch` reads the newest 100 transactions per address. An address with more gets a `PARTIAL` row where `OK` would be, because its older transactions went unchecked, and the `gsmg` address is one. A call that moves no coin in stays out. Teikhos would otherwise list every failed `authenticate` as news. A spend always counts, even an empty one. It can leak the public key.

`--since` adds the source page. `watch` takes its newest Wayback capture and the last one up to that date. If they read differently, you get a `SOURCE` row with both links and a line count. Wayback is slow, often half a minute per page. So a page that every puzzle of a collection links gets read once per pass. Pass the date of your previous run and the same old edit won't come back every night.

A check that can't run prints `FAIL`. Monero has no explorer, and an archive times out sometimes. The exit code tells a cron job what happened. It's 0 when everything it read matches, `PARTIAL` included, 1 for any finding, 2 when only lookups failed. Nothing gets written, though. A finding is for you to read. You decide if the record changes.

`puzzles_watch` is the same check for a model, one puzzle per call, with optional `since` and `apiKey`.

## Is the prize still worth a weekend?

Before you sink days into a puzzle, run the checklist. Who made it? Where's the page? Which address, which script type? Does it still hold anything? What counts as the answer? Every session used to build that by hand from `show`, `balance` and an explorer tab. Now it's one call:

```bash
puzzles eligibility gsmg                                # complete, exit 0
puzzles eligibility teikhos/0                           # two missing rows, exit 1
puzzles eligibility 1PWo3JeB9jrGwfHDNpdGK54CRas7fsVzXU  # the address finds b1000/71
puzzles eligibility 0x000000000000000000000000000000000000dEaD --chain base
puzzles eligibility gsmg --json                         # { id, …, live, evidence, conflicts, carriers, verifier, missing }
```

The `live` row is the explorer's own lifetime totals. Received and spent, the whole history, not a page of 100 transactions. That's why the busy `gsmg` address reads fine here and gets `PARTIAL` in `watch`. Mempool, Blockstream, Blockchair and dcrdata keep those totals. Etherscan, Blockscout and Arweave don't. There you get the balance and a `missing` row for the rest.

The status comes from the record, never from the chain. `unsolved` reads as `prize open`, anything else as `prize closed`. Under it sit the `evidence` rows: what the record says, the claim transaction if there is one, what the addresses hold right now. A `conflict` row is the record and the chain disagreeing. On 2 October 2026 `b1000/71` had one:

```
conflict	addresses hold 7.1019168 BTC, the record says the prize is 7.100226 BTC
```

Small deposits add up. `watch` lists them one by one.

`carrier` rows are the files and pages the clues hide in, or the key range of a range puzzle. `verifier` says what a solution is. For `gsmg` that's the private key of its uncompressed public key. For a Teikhos contract it's a `missing` row, because nothing on the record says whether an Ethereum address is a contract or a key. Guessing is easy. Guessing wrong about a contract costs you the weekend.

That's the rule for every field. Nobody fills it, it's a `missing` row with the reason. The exit code is 0 for a complete record and 1 for anything missing. An address no record holds still gets the live part and its verifier, and six `missing` rows for the rest. A bare Ethereum address also reads on Base, so it needs `--chain`.

`puzzles_eligibility` is the same record for a model, with `query`, an optional `chain` and `apiKey`.

## On this site

Every puzzle page and the playground show a live balance. The browser doesn't call the explorers itself. The docs worker does, through `/api/balance/<id>`, with the same `puzzle.balance()` call. Ethereum goes to Etherscan when the worker holds a key and to Blockscout when it doesn't. Each answer is cached for five minutes, so a busy page is one request to mempool.space, not a thousand. A failure comes back as the library's own message, `Balance lookup failed: …`, under the same status code the tool would set `isError` for.
