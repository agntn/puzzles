## One file, one literal

```ts [src/collections/b1000/71.ts]
import { bitcoinPuzzle, bits, funding, increase, p2pkh } from "@agntn/puzzles";

export const b1000Puzzle71 = bitcoinPuzzle({
  id: "b1000/71",
  address: p2pkh("1PWo3JeB9jrGwfHDNpdGK54CRas7fsVzXU", "f6f5431d25bbf7b12e8add9af5e3475c44a0a5b8"),
  sourceUrl: "https://bitcointalk.org/index.php?topic=5218972",
  startedAt: "2015-01-15 18:07:14",
  prize: 7.100226,
  key: bits(71),
  transactions: [
    funding(
      "08389f34c98c606322740c0be6a7125d9860bb8d5cb182c02f98461e5fa6cd15",
      "2015-01-15 18:07:14",
      0.071,
    ),
    increase(
      "5d45587cfd1d5b0fb826805541da7d94c61fe432259e68ee26f4a04544384164",
      "2017-07-11 05:00:53",
      0.639,
    ),
  ],
});
```

That's the whole record. No status, because unsolved is the default. No solver, no assets, no `null` anywhere. The factory picks the chain. `p2pkh` picks the address kind. `bits(71)` says the key is somewhere in `[2^70, 2^71 - 1]` and nothing more. Typo in a field name? The type checker rejects it before any test runs. And the factory freezes the literal through, nested parts included, so `puzzle.address().value = …` is refused, a `TypeError` in strict mode, instead of rewriting the record for every other reader.

## Six factories

`bitcoinPuzzle`, `ethereumPuzzle`, `litecoinPuzzle`, `decredPuzzle`, `arweavePuzzle` and `moneroPuzzle` take the same `PuzzleSpec` and answer `chain()` for it. Monero has a factory and no puzzles yet. Behind each one sits an abstract base, `BitcoinPuzzle` and so on. A puzzle that needs behavior of its own can extend a base directly. None of the :dataset-count records do.

| Field                             | Required       | Built with                                                                                                                                                 |
| --------------------------------- | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`, `sourceUrl`, `startedAt`    | yes            | strings, `YYYY-MM-DD HH:MM:SS` in UTC                                                                                                                      |
| `address`                         | yes            | `p2pkh`/`p2wpkh`/`standard` accept optional HASH160. `p2sh` requires HASH160 and accepts an optional redeem script. `p2wsh` takes only the encoded address |
| `status`                          | no, `unsolved` | `Status.Solved`, `Status.Claimed`, `Status.Swept`, `Status.Expired`                                                                                        |
| `prize`, `currency`               | no             | a number in the chain's native token, or `currency: "DAI"` when it isn't                                                                                   |
| `pubkey`                          | no             | `compressed("02…")` or `uncompressed("04…")`                                                                                                               |
| `key`                             | no             | the `Key` builder below                                                                                                                                    |
| `transactions`                    | no             | `funding`, `increase`, `decrease`, `pubkeyReveal`, `claim`, `sweep`, each `(txid, date, amount)`                                                           |
| `solvedAt`, `solveTime`, `solver` | no             | when, seconds, and `party(name, { addresses, profiles })`; an author adds `key`, `kind`, `aliases`, `about` and `facts`                                    |
| `assets`                          | no             | `assets({ puzzle, solution, hints, sourceUrl })`, file names under `assets/<collection>/`                                                                  |
| `hints`                           | no             | `official` or `community`, each `(text, source, confirmation?, { date?, answer? })`                                                                        |
| `preGenesis`                      | no             | the address predates the puzzle thread, so the funding date is the thread's                                                                                |

## Solver and solution

`solver` names the person or team, built with `party()`. `assets.solution` points to a file explaining the solution. A record can have either, both or neither.

A collection's `author` is the same `party()` with more on it: a `key` that names its page, a `kind` of `person` or `organization`, `aliases`, one line of `about`, and `facts`. A fact is `fact(text, source, { date? })`: one sentence a public page states, with that page as its source. It records who said what, not whether it's true, the same way a hint does. `authors()` lists every author with its collections and `getAuthor(key)` finds one. The [authors section](/authors) has a page per author.

For consumers of 0.20.3 and earlier, rename `assets({ solver: file })` to `assets({ solution: file })` and read `assets.solution` in JSON. `assetLinks()` now uses `kind: "solution"`, and CLI and agent output labels the link `solution asset:`. There is no alias for the old asset field. The person field and `solver()` stay unchanged, as do file paths, including Zden's existing `solver.png` URLs.

## Keys are a chain of calls

Key material comes in more shapes than any other field. So it's a builder, not a literal:

```ts
import { bits, derivation, encryptedWif, hex, seed, share } from "@agntn/puzzles";

hex("00…01", 1).wif("KwDiBf89QgGbjEhKnhXJuH7LrciVrZi3qYjgd9M7rFU73sVHnoWn"); // b1000/1
hex("af9a…4a0d").wif("5K9d…U7g").passphrase("5784623964023 578462396402"); // a brainwallet
encryptedWif("6PnW…4cH", { passphrase: "335Y-K745-C8WT-4D2W-80WP" }); // a BIP38 Ballet wallet
derivation("m/84'/0'/0'/0/0")
  .xpub("zpub6qd…JCqL")
  .shares(3, 5, [share(1, "session cigar …")]); // Bitaps
derivation("m/84'/0'/0'/0/0").entropy(
  "1808…32ed",
  source("https://twitter.com/aantonop/status/603701870482300928"),
); // Bitimage
seed("path mad alien … ghost shine", "m/84'/0'/0'/0/0"); // movie_enigma
seed("since desk thrive … ivory luggage", "m/44'/0'/0'/0/0"); // ledger_donjon
bits(71); // a search width and nothing else
```

`key()` hands back the builder. `keyData()` gives its serialized record. Every builder call returns a new builder, so `puzzle.key()?.wif(found)` gives you a key record with the WIF and leaves the puzzle as it was. `secretOf(keyData)` picks the one representation verification will use, in this order: a hex key, a decrypted WIF, an encrypted WIF, a seed phrase, a mini key. A record with only a derivation path or an xpub has no secret. `hasPrivateKey()` says `false` for it, and verification agrees.

## Hints carry their provenance

A hint is a claim about the puzzle, and the record says who made it and where. `official` is the author's, `community` is anyone else's and may be wrong. The text and its publication URL are enough: `source` is the evidence for the hint. An optional `confirmation` links to an archive capture or another page where the author published the same hint, not general information about the puzzle or a solver's reconstruction. It doesn't need a different URL from `source`. The record never says whether the hint is right.

```ts
official("Start at the top.", "https://example.com/rules");
```

Pass `undefined` as the third argument to add a date or published answer without a confirmation. Existing calls with `confirmation(url, description?)` still work:

```ts
import { confirmation, official } from "@agntn/puzzles";

official(
  "this passphrase is 2 random alphanumeric characters, such as 'X9'.",
  "https://keybase.io/warp",
  confirmation(
    "https://web.archive.org/web/20131213023906/https://keybase.io/warp/warp_1.0.6_SHA256_e68d4587b0e2ec34a7b554fbd1ed2d0fedfaeacf3e47fbb6c5403e252348cbfc.html",
    "Wayback capture of the challenge page",
  ),
); // warp/challenge_1
```

`puzzle.hints()` hands the list back in record order, empty when there is none, and `puzzles_show` prints one line per hint after the assets.

A hint that holds for every puzzle in a collection goes on the collection, once, as the fourth constructor argument next to the key, the author and the list: `super(key, author, puzzles, hints)`. A puzzle inherits those and adds its own on top. `collection.hintsFor(query)` and `collection.hintsById(id)` hand back the joined list, the collection's first, and `puzzles_show` prints the inherited ones as `collection hints` above the puzzle's `hints`. The serialized dataset carries them once per collection too, and so does the collection's page on the site, in its dossier.

### Published answers stay separate from hints

Keep the original clue in `text` and a published response in `answer`. Otherwise a solved hint stops being a hint at all. The answer has its own source and optional publication date:

```ts
import { answer, confirmation, official } from "@agntn/puzzles";

official(
  "Word #1: Presence without permanence.",
  "https://luckylurker.com/bitcoin-vault/",
  confirmation(
    "https://github.com/floflo777/open-crypto-puzzles/blob/main/4-solved/luckylurker-seed-riddles-80ksats/data/hints.csv",
  ),
  {
    date: "2026-03-17 17:30:00",
    answer: answer("visit", "https://luckylurker.com/bitcoin-vault/"),
  },
);
```

`answer` says what was published, not whether it solves the puzzle. It doesn't set `key` or change the status. CLI and tools label it separately; the site keeps it behind **Published answer** until opened. No answer given, no `answer` field in the exported record.

## Status is explicit

A claim transaction plus a published key still means `solved`. A sweep by a stranger after the public key leaked means `swept`. A prize the author took back means `expired`. Those are judgments, and the record writes them down. The library refuses to guess them from the transaction list. It would guess wrong on exactly the puzzles people care about.

## No nulls

`toJSON()` omits what a puzzle never claimed to have. No solver, no assets, no prize? Then no keys for them either. The data gate fails the build if the string `null` shows up anywhere in the dataset. Consumers check `=== undefined` once and move on.

```json
{
  "id": "b1000/71",
  "chain": "bitcoin",
  "address": { "value": "1PWo3JeB9jrGwfHDNpdGK54CRas7fsVzXU", "kind": "p2pkh", "hash160": "f6f5…a5b8" },
  "status": "unsolved",
  "key": { "bits": 71 },
  "prize": 7.100226,
  "start_date": "2015-01-15 18:07:14",
  "source_url": "https://bitcointalk.org/index.php?topic=5218972",
  "transactions": [ ... ]
}
```

The serialized names are snake case, `start_date` and `source_url`. That's what the JSON dataset looked like before this was a TypeScript package. Nothing downstream should have to care about the rewrite.

## The data gate

`pnpm test` re-checks every record. Identifiers are unique and owned by their collection. Every address and every txid fits its chain's format. A published private key derives the stored address. A decrypted WIF matches its hex. A BIP38 payload decrypts to the declared key when the passphrase is known. A claimed or swept puzzle carries a public key. Every asset path exists. Every hint stays on one line with a web URL for its source and, when present, its confirmation. Nothing serializes as null. A wrong hex digit doesn't reach `main`.
